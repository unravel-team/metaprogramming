* Quickstart

1. Copy the appropriate language folder (clojure, golang, python, or typescript) to your new project.
2. Run =make help= to see what you can do.
3. Run =make doctor= to verify your toolchain is set up correctly.
4. Run =make init= to bootstrap dependencies.

* Introduction
:PROPERTIES:
:CUSTOM_ID: h:INTRO
:CREATED:  [2026-03-10 Tue 15:30]
:END:

This repository consolidates language-specific starter scaffolds into one place and provides a single source of truth for our team's tooling conventions.

Each language scaffold follows the same Make contract, making it easy for developers to switch between languages and for AI agents to work consistently across projects.

**Why these conventions?**

- **Consistency**: Same commands across all languages reduce cognitive load
- **Discoverability**: =make help= provides immediate guidance
- **Safety**: =make doctor= catches toolchain issues early
- **Quality**: =make check= enforces code standards before commits
- **Automation**: Everything is scriptable and CI-friendly

* Common Make Targets
:PROPERTIES:
:CUSTOM_ID: h:COMMON_TARGETS
:END:

All scaffolds expose the same seven targets. This is our shared contract.

** help
:PROPERTIES:
:CUSTOM_ID: h:HELP
:END:

The =help= target displays all available commands with descriptions. It's the default target—running =make= with no arguments shows the help.

#+begin_src makefile
help:    ## Show available commands
	@awk '/^[a-zA-Z0-9_-]+:.*##/ { \
		printf "%-25s # %s\n", \
		substr($$1, 1, length($$1)-1), \
		substr($$0, index($$0,"##")+3) \
	}' $(MAKEFILE_LIST)
#+end_src

**Why this target?** Self-documenting Makefiles are crucial for onboarding. New developers can immediately see what's available without reading the entire file.

** doctor
:PROPERTIES:
:CUSTOM_ID: h:DOCTOR
:END:

The =doctor= target verifies that required toolchain is installed and available on the system.

#+begin_src makefile
.PHONY: doctor
doctor: ## Verify toolchain prerequisites
	@for cmd in <tool1> <tool2> <tool3>; do \
		command -v $$cmd >/dev/null 2>&1 || { echo "$$cmd is required"; exit 1; }; \
	done
	@echo "<Language> scaffold ready."
#+end_src

**Why this target?** Failing fast on missing tools prevents cryptic errors later. It's especially useful in CI environments where tooling may not be installed.

** init
:PROPERTIES:
:CUSTOM_ID: h:INIT
:END:

The =init= target bootstraps the project—installing dependencies, creating configuration files, and performing one-time setup.

#+begin_src makefile
.PHONY: init
init: <setup-targets> ## Bootstrap dependencies and setup
#+end_src

**Why this target?** A single entry point for setup reduces the chance of missing steps. New team members can get started with one command.

** check
:PROPERTIES:
:CUSTOM_ID: h:CHECK
:END:

The =check= target runs static analysis, linting, typing checks, and documentation validation.

#+begin_src makefile
.PHONY: check
check: <check-targets> ## Run static analysis and validation
#+end_src

**Why this target?** Running all quality checks together ensures consistency. It's what we run in CI and what we recommend running before commits.

** format
:PROPERTIES:
:CUSTOM_ID: h:FORMAT
:END:

The =format= target applies the canonical formatter for the language.

#+begin_src makefile
.PHONY: format
format: ## Apply code formatting
	<format-command>
#+end_src

**Why this target?** Automated formatting eliminates style debates and ensures consistent code. Running it as a pre-commit hook catches issues early.

** test
:PROPERTIES:
:CUSTOM_ID: h:TEST
:END:

The =test= target runs the default automated test suite.

#+begin_src makefile
.PHONY: test
test: ## Run tests
	<test-command>
#+end_src

**Why this target?** A standard test command makes CI configuration simple and provides a consistent way to run tests locally.

** build
:PROPERTIES:
:CUSTOM_ID: h:BUILD
:END:

The =build= target produces the default build artifact for the language (JAR, binary, wheel, etc.).

#+begin_src makefile
.PHONY: build
build: check <build-steps> ## Build deployment artifact
#+end_src

**Why this target?** Building artifacts as a separate step ensures they pass checks first. It also provides a standard way to create deployable outputs.

* Language-Specific Conventions
:PROPERTIES:
:CUSTOM_ID: h:LANG_CONVENTIONS
:END:

** Clojure
:PROPERTIES:
:CUSTOM_ID: h:CLOJURE
:END:

*Why this toolchain?*

- **clj-kondo**: The de facto linter for Clojure. It's fast, has excellent IDE integration, and provides meaningful error messages.
- **zprint**: A code formatter that understands Clojure's structure. We use it (not as default) because it's aggressive—formatting external libraries would cause massive diffs.
- **tagref**: Validates that references between code and documentation stay in sync. Prevents stale cross-references.
- **clojure CLI**: Official tooling with dependency management and alias support. Replaces Leiningen for new projects.

*Toolchain Requirements*

- clojure (CLI tools)
- clj-kondo
- zprint (installed via bbin)
- tagref

*Makefile Highlights*

The Clojure Makefile includes:
- =install=: One-time setup of configuration files (clj-kondo configs, zprint config, .gitignore)
- =repl=: Start a REPL with dev/test aliases
- =check=: Runs tagref, clj-kondo, and zprint checks
- =format=: Applies zprint formatting
- =test=: Runs tests via tools.build
- =build=: Creates JAR and installs to local Maven repo

*Why these choices?*

The Clojure ecosystem has converged on the CLI tools + clj-kondo + zprint combination. These tools work together seamlessly and have strong community support. The Makefile orchestrates them in a way that's both manual and CI-friendly.

See =clojure/metaclj.org= for detailed documentation of the Makefile sections.

** Golang
:PROPERTIES:
:CUSTOM_ID: h:GOLANG
:END:

*Why this toolchain?*

- **gofumpt**: Stricter gofmt. It enforces additional rules that gofmt doesn't catch, reducing style inconsistencies.
- **golangci-lint**: Aggregates many Go linters into one tool. Runs fast and provides comprehensive analysis.
- **gotestsum**: Human-readable test output. Colors and summary statistics make test results easier to digest.
- **tagref**: Validates documentation references across the codebase.

*Toolchain Requirements*

- go
- gofumpt
- golangci-lint
- gotestsum
- tagref

*Makefile Highlights*

The Go Makefile includes:
- =sync=: Download and vendor dependencies
- =install-dev-tools=: Install air, gofumpt, golangci-lint, gopls, gotestsum, tagref
- =check=: Runs golangci-lint and tagref
- =format=: Applies gofumpt formatting
- =test=: Runs tests with gotestsum
- =build:= Compiles binary to bin/

*Why these choices?*

Go has strong opinions about formatting (gofmt), and gofumpt extends those opinions. golangci-lint provides depth beyond what go vet offers. gotestsum improves the developer experience when running tests locally.

*Directory Structure*

- =cmd/=: Command-line entrypoints
- =internal/=: Private application logic
- =bin/=: Compiled binaries

** Python
:PROPERTIES:
:CUSTOM_ID: h:PYTHON
:END:

*Why this toolchain?*

- **uv**: Fast Python package installer and resolver. Replaces pip/poetry for dependency management.
- **ruff**: Extremely fast linter and formatter written in Rust. Replaces flake8, black, isort, and more.
- **pytest**: De facto standard for Python testing. Rich plugin ecosystem and clear output.
- **basedpyright**: Fast type checker (fork of Pyright). Better performance while maintaining compatibility.
- **bandit**: Security linter. Finds common security issues in Python code.
- **tagref**: Validates cross-references between code and documentation.

*Toolchain Requirements*

- python3
- uv
- ruff
- pytest
- basedpyright
- bandit
- tagref

*Makefile Highlights*

The Python Makefile includes:
- =venv=: Create virtual environment and .env file
- =install-dev-tools=: Install ruff, pytest, basedpyright, bandit, and other dev tools
- =check=: Runs ruff, basedpyright, bandit, and tagref
- =format=: Applies ruff formatting
- =test=: Runs pytest with markers for unit/integration/LLM tests
- =build:= Creates wheel distribution via uv

*Why these choices?*

uv is a game-changer for Python dependency management—orders of magnitude faster than pip. ruff consolidates multiple tools into one fast binary. basedpyright provides type checking without the overhead of mypy. Together, they provide a fast, modern Python toolchain.

*Directory Structure*

- =src/<package_name>/=/: Application code
- =tests/=: Test files (organized by type: unit/, integration/, llm/)

See =python/metapy.org= for detailed documentation of the Makefile sections.

** TypeScript
:PROPERTIES:
:CUSTOM_ID: h:TYPESCRIPT
:END:

*Why this toolchain?*

- **Bun**: Fast JavaScript runtime and package manager. Faster than npm/yarn and provides a modern dev experience.
- **Biome**: All-in-one formatter and linter. Faster than ESLint + Prettier with simpler configuration.
- **Vitest**: Fast test framework with native ESM support. Drop-in replacement for Jest with better performance.
- **tagref**: Validates cross-references between code and documentation.

*Toolchain Requirements*

- bun
- node
- tagref

*Makefile Highlights*

The TypeScript Makefile includes:
- =install=: Install dependencies via bun
- =check=: Runs Biome checks and TypeScript compiler
- =format=: Applies Biome formatting
- =test=: Runs Vitest
- =build:= Compiles TypeScript via tsc

*Why these choices?*

Bun provides a dramatically faster runtime and package manager. Biome consolidates formatting and linting into one tool—simpler config, better performance. Vitest matches Jest's API while being faster and ESM-native.

*Directory Structure*

- =src/=: Library code
- =tests/=: Test files

* How to Use These Scaffolds
:PROPERTIES:
:CUSTOM_ID: h:USAGE
:END:

1. **Choose your language**: Copy the appropriate folder (clojure, golang, python, typescript) to your new project location.

2. **Verify toolchain**: Run =make doctor= to ensure required tools are installed.

3. **Bootstrap the project**: Run =make init= to install dependencies and create configuration files.

4. **Start coding**: Edit source files, run =make test= to verify, and =make check= before committing.

5. **Format on save**: Configure your editor to run =make format= on save, or add a pre-commit hook.

6. **Build artifacts**: When ready, run =make build= to create deployment artifacts.

**Best Practices**

- Always run =make doctor= on new machines or CI environments first
- Run =make check= before committing—this catches most issues early
- Use =make help= to discover available commands
- Keep the Makefile updated with new targets as the project evolves
- Document language-specific conventions in the language's own org file

* Extending Conventions
:PROPERTIES:
:CUSTOM_ID: h:EXTENDING
:END:

**Adding a new language**

1. Create a new folder under the repo root (e.g., =rust/=)
2. Copy the Makefile template and adapt for the language
3. Ensure all 7 common targets are present
4. Add toolchain requirements to the =doctor= target
5. Create language-specific documentation following the org-mode pattern
6. Add a section to this CONVENTIONS.org file under "Language-Specific Conventions"

**Adding a new common target**

If the team agrees on a new target that all scaffolds should have:

1. Document it in the "Common Make Targets" section of this file
2. Add it to each language's Makefile
3. Ensure it follows the same naming convention and purpose across languages

**Modifying tooling choices**

When considering a tool change:

1. Document the rationale for the change in this file
2. Test the new tool in isolation first
3. Update the =doctor= target to check for the new tool
4. Update relevant Makefile targets (check, format, test, build)
5. Update the language-specific org file if one exists

**Why org-mode?**

We use org-mode for documentation because:
- It supports literate programming via org-babel-tangle
- It captures the "why" behind decisions, not just the "what"
- It's human-readable and explorable with a table of contents
- It can be edited in Emacs with rich navigation features
- It separates documentation from implementation while keeping them in sync
